## Project

"Calendaily", a daily planner. A logged-in user sees a month calendar, opens a day to manage its tasks (add/edit/delete, check off, drag to reorder, priority) and a free-text note, and is prompted to carry unfinished tasks from earlier days over to today. Built on the Laravel React starter kit (Laravel 13, Inertia v2, React 19, Tailwind v4, Fortify auth). It is served locally by Laravel Herd and uses SQLite by default.

The `<laravel-boost-guidelines>` block below is generated by Laravel Boost and rewritten by `php artisan boost:update` (which runs on `composer update`). Edit only outside that block.

## Architecture

**Data model.** `User` has many `CalendarDay` (one row per user per date, holds `note`). `CalendarDay` has many `Task` (`description`, `is_finished`, `priority` 0–3 = Low/Medium/High/Urgent, `order`). `CalendarDay::tasks()` always orders by `order`. `User::tasks()` is a `hasManyThrough`. `Task` casts `is_finished` to bool and its ids/`priority`/`order` to int; `CalendarDay::date` stays a `Y-m-d` string. A day row is created lazily: `TaskService::create()` uses `firstOrCreate` on `(user_id, date)`, so the frontend can add a task to a date that has no `CalendarDay` yet. `RecurringTask` (FEAT-09) is a repeat rule owned by a `User`; its occurrences are ordinary tasks with `recurring_task_id` set. `RecurringTaskService::generate()` creates them when `GET /api/calendar` is read, from today to the end of the grid (max a year ahead, never backfilling past days), and `generated_through` stops deleted or moved occurrences being recreated. Its date columns use the `App\Casts\DateOnly` cast so they're stored as `Y-m-d`. Occurrences are excluded from carry-over. `PUT /api/tasks/{task}/series` (`UpdateTaskSeriesRequest`) edits a task with its rule: this-and-following changes, schedule changes, starting and stopping a series. `TaskResource` has a `recurrence` field (null or the rule's schedule), mirrored by `resources/js/constants/recurrence.ts`, which `RecurringTaskTest` keeps in sync with `RepeatFrequency`.

**The app is one page and is not Inertia-driven.** `GET /` (`HomeController@index`, route `home`) renders `welcome` for guests and the `home` Inertia page for signed-in users, with the props `weekStartsOn` (`User::weekStartsOn()`: the user's setting, else `config/calendar.php`, Monday), `month`/`day`/`week` (from `?month=yyyy-MM&day=yyyy-MM-dd&week=yyyy-MM-dd`; null when absent or not a real date) and `view` (`month`, `week` or `agenda` from `?view=`, default `month`). Everything after that is client-side JSON over axios:
- `GET /api/calendar?month=YYYY-MM` (`HomeController@calendar`) returns `calendarData` keyed by `Y-m-d` date, covering the full weeks around the month (starting on `User::weekStartsOn()`, the same value the grid gets as `weekStartsOn`, so pass it to every date-fns week call), with shape `{ calendar_day: {id, note}, tasks: [...] }`. Tasks and days are serialised by `TaskResource` / `CalendarDayResource` (unwrapped: `JsonResource::withoutWrapping()` in `AppServiceProvider`), and every task endpoint returns `TaskResource`. That shape is the `CalendarData`/`DayData`/`Task` types in `resources/js/types/calendar.ts`. If you change a resource, change the type too.
- `/tasks` (store/update/destroy) and `/calendar-days` (store/update) are resource routes restricted with `->only()`. They return JSON, not Inertia responses.
- `GET /api/tasks/unfinished` returns `{ unfinishedTasks: { [date]: Task[] } }`: the user's unfinished tasks on days strictly before today, from any month, oldest first.
- `POST /api/tasks/carry-over` (`CarryOverTasksRequest`) takes `{ task_ids }` and appends those tasks to the user's day for today, which the server finds or creates. It returns 403 if any id isn't the user's and 422 if any task is finished or not from a past day.
- `PUT /api/tasks/{task}/move` (`MoveTaskRequest`) takes `{ date }` and appends the task to the user's day for that date, which the server finds or creates (`TaskService::moveTask`). The frontend's `hooks/use-move-task.ts` removes it from its day in every cached month at once and places the server's copy on success.
- `PUT /api/tasks/reorder` (`ReorderTasksRequest`) takes one day's tasks in their new order and rewrites `order` as 1..n in a single `CASE` update. It returns 422 if the tasks span more than one day.

**Time zone and week start (FEAT-01).** `users.timezone` and `users.week_starts_on` are set under Settings → Calendar (`Settings\CalendarSettingsController`, `/settings/calendar`). The browser sends its IANA zone in an `X-Timezone` header on every axios request (set in `resources/js/app.tsx`), and the `StoreDetectedTimezone` web middleware saves it on a user whose `timezone` is null. Server code that needs "today" must use `App\Support\UserClock::today($request)`: the stored zone, else the header, else `config('app.timezone')` (UTC). Never call `now()` for the user's date. Client code must likewise take "today" from `lib/clock.ts` (`today()`, `isToday()`, `isTomorrow()`, `isBeforeToday()`), never `new Date()` or date-fns `isToday`; `app.tsx` points it at `auth.user.timezone` on every page. Weekly repeat rules use `User::weekStartsOn()` too, and saving the settings clears the query cache.

Business logic lives in `app/Services/TaskService.php`, which `TaskController` receives through constructor injection.

**Frontend flow.** `resources/js/pages/home.tsx` reads the visible month and selected day from its `month`/`day` props, so the URL is the source of truth: navigating calls Inertia's client-side `router.push`/`router.replace` with new props (no server round trip), and back/forward restore them. It shows `CalendarHeader` (with the Month/Week/Agenda switcher) over `MonthGrid` → `DayCell`, `WeekView` or `AgendaView`, or the `DayView` (→ `DayPanelContent`). Week URLs carry `week` and no `month`: the week view reads the cached query of the month the week starts in, whose grid always contains the whole week. Query params in `homeUrl()` stay alphabetical (`day`, `month`, `view`, `week`). Keyboard shortcuts (FEAT-07) are wired in `home.tsx` through `hooks/use-keyboard-shortcuts.ts`, a window `keydown` listener that skips events that are `defaultPrevented` (dnd-kit keyboard drags, Radix roving focus), typed into fields, or sent while a dialog or menu is open. `SHORTCUTS` there feeds the `?` help dialog. `n` reaches the day view as the `addTaskRequested` prop. The week and agenda views check tasks off with `hooks/use-toggle-finished.ts` and the week view drags tasks between days (dnd-kit `useDraggable`/`useDroppable`) through `useMoveTask`. Data goes through **TanStack Query** (`QueryClientProvider` in `app.tsx` and `ssr.tsx`, client from `lib/query-client.ts`). `lib/calendar-api.ts` has the query keys and one axios function per endpoint; components never call axios directly. `hooks/use-calendar.ts` reads the visible month's query (`['calendar', 'yyyy-MM']`, kept on screen with `keepPreviousData` while the next month loads), fetches `['tasks', 'unfinished']` whenever the month view is shown (a non-empty result opens `UnfinishedTasksDialog`, where the user ticks which tasks to move; "Not now" or a carry-over stores today's date in `localStorage`, per user, and the prompt stays away until tomorrow), and does the carry-over, which invalidates every `['calendar']` query. `hooks/useTaskActions.ts` runs the per-day mutations with `useMutation` and, on success, patches the visible month's cache through an `updateData(prev => next)` callback (`setQueryData`). It does not fetch again. Two exceptions: reordering is optimistic (applied in `onMutate`, rolled back in `onError`), and a delete hides the task at once but is only sent after a 5-second Undo toast (timers in `lib/pending-deletes.ts`). Errors are handled once, in `lib/query-client.ts`: a failed query or mutation shows a `sonner` toast titled with its `meta.errorMessage` (the reason comes from `errorReason()` in `lib/errors.ts`), and a failed mutation refetches every `['calendar']` query. Give every new `useQuery`/`useMutation` a `meta.errorMessage` instead of an `onError` that logs. Forms that show 422s next to their fields set `meta.inlineValidation` and read them with `validationErrors(mutation.error)`. The day's note autosaves through `hooks/use-note-autosave.ts` (800 ms after typing stops, on blur, and on leaving the day), one save at a time so the first save, which creates the day row, is never raced by a second create. Drag-and-drop reordering uses `@dnd-kit` in `day-panel-content.tsx` / `sortable-task.tsx`. The day view's sort and "Hide completed" choice (FEAT-05) lives in `hooks/use-task-list-view.ts` (in `localStorage`, client-only): drags work on the shown list, only in "My order", and `mergeReorder()` keeps hidden tasks in their places. Priority is the `App\Enums\Priority` enum (cast on `Task`, validated with `Rule::enum`, `Priority::DEFAULT` = Medium). `resources/js/constants/priority.ts` mirrors its values, labels and default plus the colours, and `PriorityTest` fails if they drift, so change both together.

**Wayfinder.** `resources/js/actions`, `resources/js/routes` and `resources/js/wayfinder` are generated by the Vite plugin and gitignored. Every axios call takes its URL from the generated controller actions (e.g. `TaskController.update.url(id)` from `@/actions/App/Http/Controllers/TaskController`), never a hardcoded string. After adding or renaming a route, run `php artisan wayfinder:generate --with-form` (or let Vite do it) before type-checking.

**Authorization.** `TaskPolicy` (ownership through `calendarDay.user_id`) and `CalendarDayPolicy` are checked with `Gate::authorize()` in the controllers' `update`/`destroy`. The bulk endpoints check ownership in `TaskService`: `reorderTasks`/`carryOverTasks` throw `AuthorizationException` (403) if any id isn't the user's, and only touch the user's tasks. The Form Requests' `authorize()` methods only check `Auth::check()`, so any new endpoint must authorize explicitly.

**Tests.** Each domain area has a feature test: `CalendarApiTest` (range and response shape), `TaskCrudTest`, `CalendarDayNoteTest`, `ReorderTest`, `CarryOverTest`, `MoveTaskTest`, `RecurringTaskTest`, `AuthorizationTest` (cross-user access), `UserTimezoneTest`, `Settings\CalendarSettingsTest` (FEAT-01 settings, detection and week start) and `ValidationTest`. Factory states: `RecurringTask::factory()->weekly([...])`, `->monthly()`, `->startingOn('Y-m-d')`, `CalendarDay::factory()->onDate('Y-m-d')`, `->past()`, `->future()`, `->withNote()`, and `Task::factory()->finished()`, `->priority(n)`.
